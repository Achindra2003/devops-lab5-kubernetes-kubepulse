       19 +### The Challenge with Naive Kubernetes Deployments           
       20 +The usual first Kubernetes exercise is `kubectl create deploym
          +ent`, `kubectl expose` and one `kubectl scale`. The commands w
          +ork, but the manifest that results has serious operational wea

       21 
       21 -**KubePulse** is a zero-dependency Node.js service that report
          -s the Pod, node and version that served each request, exposes 
          -readiness/liveness endpoints, can burn CPU on demand (for the 
          -autoscaler) and has lab-only chaos endpoints (unready, crash).
          - One Dockerfile produces three releases: `1.0.0`, `2.0.0`, and

       22 +1. **Update Outages:** The `Recreate` strategy (or an unprobed
          + rolling update) removes capacity before replacements are read
          +y. Users see connection errors on every release.              
       23 +2. **Traffic to Unready Pods:** Without a readiness probe, a S
          +ervice routes requests to a container the moment it starts, be
          +fore the application can answer.

          +dline and `maxUnavailable: 0`, a broken image replaces healthy
          + Pods, turning a deploy into an incident.                     
       25 +4. **Static Capacity:** A fixed replica count wastes resources
          + when idle and saturates under load; without CPU requests the 
          +autoscaler cannot work at all.                                
       26 +5. **Unhardened Containers:** Default security context leaves 
          +a writable root filesystem, default Linux capabilities and no 
          +seccomp profile.

      112 +```yaml

      115 +metadata: { name: kubepulse, namespace: kubepulse }           
      116 +spec:
